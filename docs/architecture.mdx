## Overview

ShipSec Studio is the harness layer that connects:

- workflow design
- durable execution
- agents and MCP tools
- secrets and runtime credentials
- human approvals
- run observability

At a high level:

```
Frontend → Backend → Temporal → Worker → Tools / MCP / APIs / Scanners
```

## Core Runtime Model

### Frontend

The frontend provides:

- workflow design
- chat and agent UX
- settings and integrations
- run visibility
- cloud, code security, and ASM surfaces

### Backend

The backend owns:

- APIs
- auth and organization context
- secrets and storage metadata
- schedules and webhooks
- templates and report templates
- MCP and integration control surfaces
- trace, audit, and artifact APIs

### Temporal

Temporal gives Studio:

- durable workflow execution
- retries
- pause/resume behavior
- long-running waits
- workflow-level state management

### Worker

The worker executes:

- components
- agent steps
- MCP discovery/runtime steps
- scanner calls
- cloud and GitHub tasks
- human-in-the-loop activities

## Why This Fits The “Harness” Model

Studio is not only about defining steps.

It provides the execution frame around those steps:

- tools have lifecycle
- credentials resolve at runtime
- humans can interrupt and resume safely
- runs are visible and auditable
- workflows can be reused and scheduled

That is why “harness” is the right framing.

## Self-Hosted Default

The public repo is designed for self-hosted, usually single-tenant operation.

That means the architecture you should think about first is:

- one deployment
- your own credentials
- your own AI provider config
- your own integrations

ShipSec Cloud is the managed hosted offering, but public architecture docs should focus on the self-hosted system first.
