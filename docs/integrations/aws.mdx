Studio’s AWS integration model is built for runtime credential resolution inside
workflows.

Use it when you need:

- cloud posture scans
- organization account discovery
- cross-account AssumeRole flows
- inventory and cloud graph ingestion

## OSS Setup Path

Common self-hosted paths:

- access keys for the simplest community-edition setup
- IAM role or AssumeRole configuration for short-lived credentials and stronger isolation
- AWS Organizations discovery for multi-account workflows

## Two Public AWS Routes

### Access Key

Use this when you want the simplest self-hosted setup:

- create an AWS access key and secret key
- store that connection in Studio
- let workflows resolve those credentials at runtime

### IAM Role / AssumeRole

Use this when you want:

- short-lived credentials
- stronger separation between Studio and the target account
- easier revocation through IAM trust policy changes

## How AWS Fits Into Workflows

A common public flow is:

1. configure an AWS connection
2. resolve credentials at runtime inside a workflow
3. feed those credentials into scanners or inventory steps
4. write findings into analytics or downstream notifications

## Common AWS Workflows

- Prowler-based cloud posture scans
- organization account discovery
- inventory and graph indexing
- alerting and reporting on cloud findings

## Recommended Mental Model

The workflow should reference the AWS connection, not long-lived raw secrets in
the graph itself.

That keeps the AWS setup reusable regardless of whether the backend is a stored
access key or an assumed role.

## Self-Hosted vs ShipSec Cloud

ShipSec Cloud runs the same AWS capability in the hosted deployment.

In self-hosted Studio, AWS setup remains direct and operator-managed.
