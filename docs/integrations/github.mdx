GitHub is one of Studio’s richest integration surfaces.

Use it when you need:

- repository access
- pull-request scanning
- check runs and PR comments
- trigger rules for automated scans
- AI review or security workflows tied to GitHub events

## OSS Setup Path

For the actual Studio GitHub product surface, a GitHub App is the primary
self-hosted path.

That is the path required for:

- installation-aware repository access
- PR webhooks
- trigger rules
- check runs
- PR comments and review-style feedback

In practice, self-hosted Studio already works as BYOA:

- you create or own the GitHub App
- you set the app credentials in Studio config
- you install that app into the repositories or organizations you want Studio to manage

A PAT can still make sense for narrower custom automation outside this main App
surface, but it is not the first-class path for PR-triggered GitHub workflows in
Studio today.

## What The GitHub Surface Covers

Studio’s GitHub features include:

- repository sync and scan targets
- PR-triggered workflows
- PR comments
- check runs
- optional inline review-style feedback

## Typical Flow

A common GitHub security workflow looks like:

1. pull request or repository event enters Studio
2. Studio clones or reads the relevant repository context
3. scanners and AI steps analyze the code or diff
4. results are posted back to GitHub as comments, checks, or reviews

## Trigger Rules

Trigger rules connect GitHub events to workflows.

Typical uses:

- run a security scan on every PR
- comment on findings when a PR changes
- fail checks above a severity threshold

## Self-Hosted vs ShipSec Cloud

In ShipSec Cloud, the onboarding flow can be more managed.

In self-hosted Studio, the GitHub App model is still the right mental model:

- bring your own app
- configure Studio with that app’s credentials
- install the app where you want repository and PR automation

That gives self-hosted users the same core GitHub capability surface without
requiring a ShipSec-managed app.

## What PAT Can And Cannot Do

PAT-based access is not enough for the full GitHub product surface.

What a PAT does **not** give you:

- inbound GitHub App installation events
- GitHub App webhooks
- installation-token-based repository access
- the main repository/trigger-rule/check-run product flow in Studio

So if you want PR webhooks and the richer GitHub automation surface, the answer
is BYOA via GitHub App, not PAT-only setup.
