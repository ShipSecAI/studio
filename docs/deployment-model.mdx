## Public Positioning

ShipSec Studio is an open-source platform for self-hosted, agent-native security workflow orchestration.

The public repo should be understood as:

- **self-hosted first**
- **single-tenant by default**
- **operator-controlled**

That means the open-source product expects you to:

- run the app stack yourself
- own your own infrastructure and credentials
- choose your own AI provider configuration
- choose your own integration setup path

## What “Single-Tenant” Means Here

For the public repo, the default mental model is:

- one deployment
- one team or one organization operating it
- one set of credentials and runtime services under your control

Studio still has organization and auth concepts internally, but the open-source docs should not pretend this repo is a hosted multitenant SaaS by default.

## Supported Public Paths

### 1. Self-Hosted Deployment

Use the published application images in your own runtime model and infrastructure layout.

### 2. Source Development

Use this if you are contributing or developing from source:

`just init` and `just dev` remain the source-development entrypoints.

## ShipSec Cloud

ShipSec Cloud is the managed hosted offering.

It is the hosted deployment of the same product capabilities.

ShipSec operates the hosting and the hosted-only provider paths there.

## OSS vs Managed Principle

The rule for public docs is:

- describe the same capability class in both worlds
- explain the OSS setup path directly
- mention the managed option without exposing internal implementation details

Examples:

- AI in OSS: model ID + base URL + API key
- GitHub in OSS: BYOA GitHub App
- AWS in OSS: access keys or IAM role setup
- GCP in OSS: service account JSON or impersonation
- Jira in OSS: Atlassian OAuth or a self-managed Jira app and web trigger
- Slack in OSS: webhook or Slack app
- local CE runtime in OSS: `docker/docker-compose.infra.yml` with `just dev`, or `docker/docker-compose.infra.yml` + `docker/docker-compose.apps.yml`
