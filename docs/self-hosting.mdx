## What Self-Hosting Means Here

ShipSec Studio open source is designed first for **self-hosted, usually single-tenant deployments**.

That means:

- you run the app stack yourself
- you manage your own credentials and provider setup
- you decide how much infrastructure you want to own

This public repo intentionally focuses on the application and image build surface.

## What A Studio Deployment Needs

Studio expects a deployment to provide these service classes:

- frontend
- backend
- worker
- PostgreSQL
- Temporal
- Redis
- MinIO
- Loki
- Redpanda
- ClickHouse
- Neo4j
- Hotplug

How you provide those is up to you.

## Published Images

The public repo publishes application images such as:

- `ghcr.io/shipsecai/studio-backend:latest`
- `ghcr.io/shipsecai/studio-worker:latest`
- `ghcr.io/shipsecai/studio-frontend:latest`

## Authentication

Self-hosted deployments can use local auth or external auth depending on how you configure the backend.

## AI Configuration

AI is optional in self-hosted mode.

If you want AI components and agent flows to call your provider directly, configure:

```bash
export CHAT_AI_BASE_URL="https://api.openai.com/v1"
export CHAT_AI_API_KEY="..."
export CHAT_AI_MODEL_ID="gpt-5.4-mini"
```

## How To Make It Your Own

Typical self-hosted customizations:

- replace image tags with pinned versions
- provide your own PostgreSQL, Temporal, Redis, object storage, analytics, and runtime services
- inject external auth configuration
- add provider credentials and integrations
- change ingress, networking, and persistence policies
